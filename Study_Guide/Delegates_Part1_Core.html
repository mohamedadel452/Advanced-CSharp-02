1) المشكلة اللي بيحلها الـ Delegate (سلايد 5)

عندك دالة بتعمل خطوات ثابتة، بس خطوة واحدة جواها بتتغير من حالة لحالة (طريقة حساب الخصم مثلاً). من غير delegate هتكتب شرط لكل حالة:

static decimal Checkout(decimal price, string customerType) => customerType switch
{
    "student" => price * 0.5m,
    "vip"     => price * 0.8m,
    _         => price
};
// كل نوع عميل جديد = تعديل الدالة دي (تكسر Open/Closed، وتحتاج re-test لكل شيء)

الحل: خلّي الخطوة المتغيرة باراميتر. الدالة متعرفش الخصم بيتحسب إزاي، بس تعرف شكله (بياخد decimal ويرجع decimal):

delegate decimal Discount(decimal price);

static decimal Checkout(decimal price, Discount discount) => discount(price);

Checkout(100m, p => p * 0.5m);   // student
Checkout(100m, p => p * 0.8m);   // vip
Checkout(100m, p => p);          // عادي، ومن غير ما نلمس Checkout

الفكرة الأعمق: ده نفس اللي بتعمله بالـ interface في الـ Strategy pattern (IDiscountStrategy)، لكن من غير class و interface كاملين لسلوك من سطر واحد.

2) إيه هو الـ Delegate؟ (سلايد 4)

التشبيه: ريموت التلفزيون. الريموت مش بيعمل التشغيل بنفسه، بس بيشاور على جهاز (method) معين. تبدّل الجهاز اللي الريموت متوصل بيه من غير ما تغيّر الريموت.

التعريف الدقيق: الـ delegate نوع (type) بيمثّل "شكل" دالة: أنواع الـ parameters + نوع الـ return. أي متغير من النوع ده ممكن يشاور على أي دالة بنفس الشكل. وهو type-safe: الـ compiler بيفحص الـ signature.

تصحيح لتعبير "function pointer": السلايد بيقول "type-safe function pointer"، وده تبسيط مقبول، لكن الـ delegate object على الـ Heap مش مجرد عنوان. بيحمل كمان الـ this اللي هتتنفذ عليه الدالة (Target)، وده اللي بيخليه أقوى من C function pointer، وهو سبب مشكلة الـ memory leak اللي هنشوفها.

3) الميكانيزم: المترجم بيعمل إيه؟

لما تكتب delegate int MathOperation(int a, int b); المترجم بيولّد class كامل:

// المتولّد تقريباً
public sealed class MathOperation : MulticastDelegate
{
    public MathOperation(object target, IntPtr method);
    public int Invoke(int a, int b);     // ينفذ الدالة (أو الـ invocation list)
}
  • استدعاء d(10, 5) هو سكر نحوي لـ d.Invoke(10, 5).
  • الـ delegate immutable: كل += أو -= بيعمل delegate جديد (Delegate.Combine) ويستبدل المتغير.
  • التساوي: delegateين متساويين لو نفس الـ Target ونفس الـ Method.
  • عشان كده Delegate reference type (class) مش struct، وكل إنشاء لواحد جديد = allocation على الـ Heap.
class Calc { public int Mul(int a, int b) => a * b;  public static int Add(int a, int b) => a + b; }

MathOperation s = Calc.Add;            // static
MathOperation i = new Calc().Mul;      // instance
Console.WriteLine(s.Target is null);   // True  (مفيش this)
Console.WriteLine(i.Target is Calc);   // True  (الـ delegate ماسك الـ object)
Console.WriteLine(s.Method.Name);      // Add

4) التعريف والإنشاء والاستدعاء (سلايد 7 و 8)

public delegate int MathOperation(int a, int b);          // 1) التعريف: signature فقط

static int Add(int a, int b)      => a + b;
static int Subtract(int a, int b) => a - b;
static int Multiply(int a, int b) => a * b;

MathOperation op1 = new MathOperation(Add);   // الشكل القديم (C# 1)
MathOperation op2 = Subtract;                 // Method Group Conversion
MathOperation op3 = (a, b) => a * b;          // Lambda

Console.WriteLine(op1(10, 5));   // 15
Console.WriteLine(op2(10, 5));   // 5
Console.WriteLine(op3(10, 5));   // 50

قواعد التطابق (وفيها نقطة السلايد ما بيذكرهاش)

السلايد بيقول "الـ signature لازم يتطابق بالظبط". ده غير دقيق. في C# فيه variance للـ delegates مع reference types:

delegate object Factory(string s);

static string Make(object o) => o.ToString()!;
// parameter: object أوسع من string  (Contravariance: يقبل أي string)
// return   : string أضيق من object  (Covariance: يرجع حاجة تنفع كـ object)
Factory f = Make;    // يشتغل

ومع value types (int مقابل long مثلاً) مفيش variance: لازم تطابق تام في النوع.

5) الـ Delegate كـ Parameter (سلايد 9): Strategy من الواقع

public delegate bool Rule(Order order);

public class OrderValidator
{
    private readonly List<(string Name, Rule Check)> _rules = new();
    public OrderValidator Add(string name, Rule rule) { _rules.Add((name, rule)); return this; }
    public IEnumerable<string> Validate(Order o) => _rules.Where(r => !r.Check(o)).Select(r => r.Name);
}

var validator = new OrderValidator()
    .Add("Has items",    o => o.Items.Count > 0)
    .Add("Positive total", o => o.Total > 0)
    .Add("Under limit",  o => o.Total < 100_000);

var failed = validator.Validate(order).ToList();   // أسماء القواعد اللي فشلت
public record Order(List<string> Items, decimal Total);

إمتى هتحتاجه: قواعد تحقق (validation rules) بتتغير من عميل لعميل، أو خطوات معالجة بتتبدل، أو callbacks. بدل ما تعمل class لكل قاعدة تضيف سطر.

الـ Delegates هي أساس الـ ASP.NET Core middleware

Request→Logging→Auth→Endpoint←Auth←Logging←Response
app.Use(async (context, next) =>      // next هو delegate للـ middleware اللي بعده
{
    var sw = Stopwatch.StartNew();
    await next();                        // استدعاء الباقي
    Console.WriteLine($"{context.Request.Path} took {sw.ElapsedMilliseconds} ms");
});

كل middleware بياخد delegate للي بعده ويقرر ينفذه أو لا (مثلاً الـ Auth يوقف الطلب). ده ثمرة فهم الـ delegates فعلاً.

6) Multicast Delegates (سلايد 10 إلى 13)

الـ delegate ممكن يشاور على أكتر من دالة. الدوال بتتخزن في invocation list وبتتنفذ بترتيب الإضافة.

d→[ Method1 ]→ then →[ Method2 ]→ then →[ Method3 ]
delegate void MyDelegate(string msg);
static void M1(string m) => Console.WriteLine($"Method1: {m}");
static void M2(string m) => Console.WriteLine($"Method2: {m}");
static void M3(string m) => Console.WriteLine($"Method3: {m}");

MyDelegate d = M1;
d += M2;
d += M3;
d("Hello");      // Method1, Method2, Method3 بالترتيب
d -= M2;         // يشيل M2
d("Again");      // Method1, Method3

الحقيقة اللي جوه: d += M2 هي d = (MyDelegate)Delegate.Combine(d, new MyDelegate(M2)). و-= بتشيل آخر ظهور مطابق للدالة، ولو مش موجودة ما بترميش exception.

الـ Return Value (سلايد 12 و 13): آخر واحدة بس

Func<int> f = () => 1;
f += () => 2;
f += () => 3;
Console.WriteLine(f());      // 3  (القيم 1 و 2 اتنفذت واتضيعت)

foreach (var h in f.GetInvocationList().Cast<Func<int>>())
    Console.WriteLine(h());  // 1 ثم 2 ثم 3: لو عايز كل النتائج

ليه كده؟ الـ compiler مش عارف يدمج n نتائج في نتيجة واحدة، فالقاعدة بسيطة: ترجع آخر نتيجة. لو محتاج كلها: GetInvocationList().

7) مشاكل حقيقية في الإنتاج

1) NullReferenceException على delegate فاضي

Action? onDone = null;
onDone();        // NullReferenceException
onDone?.Invoke(); // الصح

2) استثناء في واحدة بيوقف الباقي

Action a = () => Console.WriteLine("A");
a += () => throw new Exception("boom");
a += () => Console.WriteLine("C");
try { a(); } catch { }       // طُبع A فقط، C ما اتنفذتش

// الحل لما كل subscriber مستقل (إشعارات مثلاً):
foreach (var h in a.GetInvocationList().Cast<Action>())
    try { h(); } catch (Exception ex) { Console.WriteLine($"handler failed: {ex.Message}"); }

3) Memory leak من الاشتراك في events (الأشهر)

class Publisher { public event EventHandler? Changed; }          // عمره طويل (singleton)
class Screen
{
    public Screen(Publisher p) { p.Changed += OnChanged; }       // الاشتراك
    void OnChanged(object? s, EventArgs e) { }
}
// كل Screen بتتعمل بتتسجل في الـ invocation list بتاعة Publisher.
// الـ delegate بيحمل Target = Screen، فـ GC مش هيجمعها أبداً.

الحل: p.Changed -= OnChanged في Dispose، أو weak events، أو تأكد إن عمر الـ publisher مش أطول من الـ subscriber. ده في WPF و Blazor Server و الـ background services سبب شائع جداً لتضخم الذاكرة.

4) delegateين بنفس الـ signature مش قابلين للتبديل

Predicate<int> p = n => n > 0;
// Func<int,bool> f = p;                       // CS0029
Func<int,bool> f = new Func<int,bool>(p);      // يشتغل (delegate يلف delegate)

كل نوع delegate هو class مستقل، فمفيش علاقة وراثة بين Predicate<int> و Func<int,bool> مهما كان الشكل متطابق.

5) Thread safety: handler += x مش atomic في الـ field العادي. لو بتشترك من أكتر من thread استخدم event (المترجم بيضيف Interlocked في الـ accessors) أو lock.
