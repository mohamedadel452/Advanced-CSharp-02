1) ليه Built-in Delegates؟ (سلايد 15 إلى 19)

في الأول كل مبرمج كان يعرّف delegate خاص بيه لكل شكل (delegate void LogHandler(string s)) وبتتكرر مئات المرات. من .NET 2.0 و 3.5 المكتبة عرّفت أشكال عامة (generic) جاهزة في System، وبقت الأنواع القياسية اللي كل الـ APIs بتتفق عليها.

2) Func مقابل Predicate، وإمتى تكتب delegate خاص

  • Predicate<T> قديم، ظهر مع الـ List<T> (.NET 2.0). وFunc<T,bool> هو اللي استخدمه LINQ. ولو كتبت API جديد استخدم Func<T,bool> لأنه المعيار في الـ LINQ. (سلايد 20 سؤال 4 فيه إجابتين مقبولتين لنفس السبب.)
  • ممنوع ref و out في Func/Action لأنها type parameters عادية. لو محتاج، عرّف delegate خاص:
delegate bool TryParser<T>(string input, out T value);

static bool ParseAll<T>(string[] items, TryParser<T> parser, out List<T> result)
{
    result = new();
    foreach (var s in items)
    {
        if (!parser(s, out var v)) return false;
        result.Add(v);
    }
    return true;
}
ParseAll(new[] { "1", "2" }, int.TryParse, out var ints);   // method group يختار الـ overload المناسب

وكمان لما تحتاج اسم يعبّر عن المعنى (delegate decimal TaxPolicy(decimal amount) أوضح للقارئ من Func<decimal,decimal> في API عام).

3) Anonymous Methods (سلايد 23 إلى 26)

الفكرة: دالة من غير اسم بتكتبها في مكان استخدامها بدل ما تعرّف method منفصلة لاستخدام مرة واحدة.

Action<string> greet = delegate (string name) { Console.WriteLine($"Hello, {name}!"); };

Func<int, int, int> multiply = delegate (int a, int b) { return a * b; };

Action quick = delegate { Console.WriteLine("بدون parameters"); };   // قائمة الـ parameters ممكن تتشال
النسخةالشكلإضافة
C# 1.0new Handler(MethodName)named method بس
C# 2.0delegate (int x) { ... }Anonymous methods و closures
C# 3.0x => ...Lambda و LINQ و Expression Trees

تصحيح (سلايد 25): السلايد بيقول إن الـ lambda "syntactic sugar over anonymous methods". ده مش دقيق. الاتنين بيتحولوا لنفس نوع الكود (closure و method مولّدة)، لكن الـ lambda ليها قدرات مالهاش anonymous method: (1) ممكن تتحول لـ Expression Tree (EF Core بيعتمد عليها)، (2) الـ natural type (C# 10)، (3) كتابة مختصرة بتقبل الاستنتاج. الـ anonymous method بتفيد في حالة واحدة: delegate { } لما ما تحتاجش الـ parameters.

4) Lambda Expressions (سلايد 28 إلى 30)

Action sayHello = () => Console.WriteLine("Hello");               // من غير parameters
Action<string> greet = name => Console.WriteLine($"Hi {name}");    // واحد: الأقواس اختيارية
Func<int, int, int> mul = (x, y) => x * y;                         // أكتر: الأقواس إجبارية

Func<int, string> kind = n =>                                      // Statement lambda
{
    if (n > 0) return "Positive";
    return n < 0 ? "Negative" : "Zero";
};

إمكانيات حديثة مهمة

var square = (int x) => x * x;               // C# 10: natural type = Func<int,int>
var log = (string m) => Console.WriteLine(m); // natural type = Action<string>
Func<int, int> twice = static x => x * 2;   // C# 9: static lambda ممنوع يعمل capture

ليه الـ lambda "ملهاش نوع"؟ لأنها مجرد شكل. نفس الـ x => x * 2 ممكن تتحول لـ Func<int,int> أو لـ Expression<Func<int,int>> أو لـ delegate خاص، والـ compiler بيختار من النوع المتوقع.

5) Closures: أهم وأخطر جزء

الـ lambda ممكن تستخدم متغيرات من الدالة اللي حواليها (سلايد 25 و 31 سؤال 6). السلايد بيقول الأسئلة، لكن مش بيشرح إزاي.

static Func<int> MakeCounter()
{
    int count = 0;
    return () => ++count;       // بتستخدم count بعد ما MakeCounter تخلص!
}
var c1 = MakeCounter(); var c2 = MakeCounter();
c1(); c1(); c2();
Console.WriteLine($"{c1()} {c2()}");   // 3 2  (كل واحد عنده count خاص)

الميكانيزم

المتغير count المفروض يموت لما الدالة تخلص (Stack). عشان كده المترجم بيرفعه لحقل في class مولّدة على الـ Heap، والـ lambda تتحول لـ method داخل نفس الـ class، والـ delegate بيشاور على object منها (Target).

الحقائق المهمة

  • الـ closure بيمسك المتغير نفسه مش قيمته وقت الإنشاء (إجابة سلايد 31 سؤال 6: by reference).
  • تغيير المتغير بعد إنشاء الـ lambda بيتشاف جواها، والعكس.
  • عمر المتغير = عمر الـ delegate. لو الـ delegate اتخزن في static field، المتغير (وكل اللي بيشاور عليه) مش هيتجمع.

باگ كلاسيكي: for loop

var actions = new List<Action>();
for (int i = 0; i < 3; i++) actions.Add(() => Console.Write(i));
actions.ForEach(a => a());              // 3 3 3   (i واحد مشترك، وقيمته بعد الحلقة 3)

foreach (var n in new[] { 0, 1, 2 }) actions.Add(() => Console.Write(n));   // 0 1 2
// ملحوظة: foreach بيعمل متغير جديد كل دورة من C# 5

for (int i = 0; i < 3; i++) { int copy = i; actions.Add(() => Console.Write(copy)); }   // الحل في for

ده بيظهر كتير في Task.Run(() => Process(i)) داخل for: كل المهام بتشوف نفس i وقت التنفيذ.

التكلفة: الـ lambda اللي مش بتعمل capture بيتخزن delegate واحد بتاعها في حقل static وبيتعاد استخدامه (من غير allocation). أما اللي بتعمل capture فبتنشئ DisplayClass و delegate جديدين كل مرة الدالة تتنادى. في hot path (ملايين الاستدعاءات) ده بيضغط على الـ GC. استخدم static lambda عشان المترجم يمنع الـ capture بالغلط.

6) Func مقابل Expression<Func>: فخ الأداء في EF Core

Expression<Func<int, bool>> e = n => n > 5;
Console.WriteLine(e.Body);            // (n > 5)  ← الـ lambda كبيانات (شجرة)
Func<int, bool> f = e.Compile();     // تحويل الشجرة لكود
Console.WriteLine(f(7));              // True

مع Func الكود بيتنفذ في الـ CLR. مع Expression المكتبة (EF Core) بتقرأ الشجرة وتترجمها لـ SQL. وده السبب إن IQueryable.Where بتاخد Expression، وIEnumerable.Where بتاخد Func.

باگ إنتاج حقيقي:

Func<Product, bool> expensive = p => p.Price > 100;
var a = db.Products.Where(expensive).ToList();      // SELECT * FROM Products  ← الجدول كله لذاكرتك!
                                                    // وبعدين الفلترة في الـ C#
Expression<Func<Product, bool>> expensive2 = p => p.Price > 100;
var b = db.Products.Where(expensive2).ToList();     // SELECT ... WHERE Price > 100

أي دالة بتبني فلاتر قابلة لإعادة الاستخدام على EF لازم تاخد Expression<Func<T,bool>> مش Func. وده من أكتر أسباب بطء الـ API بعد زيادة البيانات.

7) الـ async lambdas: Action مقابل Func<Task>

Action bad = async () => { await Task.Delay(100); throw new Exception("x"); };
bad();            // async void: مفيش حد يستنى، والـ exception ممكن تقفل الـ process

Func<Task> good = async () => { await Task.Delay(100); throw new Exception("x"); };
try { await good(); } catch (Exception e) { /* تتمسك هنا */ }

items.ForEach(async x => await SaveAsync(x));              // fire-and-forget، مش هيستنى حاجة
await Task.WhenAll(items.Select(x => SaveAsync(x)));        // الصح

ليه؟ الـ lambda async () => ... بتتحول لـ delegate يرجع Task لو الهدف Func<Task>، ولو الهدف Action فبتبقى async void (مفيش Task يرجع، فمفيش مكان تتجمع فيه الأخطاء). كل API بيقبل callback async لازم يقبل Func<Task>.

8) أنماط من المشاريع الحقيقية

// 1) Retry لأي عملية شبكة
static async Task<T> Retry<T>(Func<Task<T>> op, int attempts = 3)
{
    for (var i = 1; ; i++)
        try { return await op(); }
        catch when (i < attempts) { await Task.Delay(200 * i); }
}
var user = await Retry(() => http.GetFromJsonAsync<User>("/users/1"));

// 2) Strategy table بدل switch
var ops = new Dictionary<string, Func<decimal, decimal, decimal>>
{
    ["+"] = (a, b) => a + b, ["-"] = (a, b) => a - b, ["*"] = (a, b) => a * b
};
Console.WriteLine(ops["*"](3, 4));    // 12

// 3) Lazy و caching بـ factory delegate
var cache = new Lazy<Config>(() => LoadConfig());

// 4) Guard clause بتحوّل exception
static T Try<T>(Func<T> f, T fallback) { try { return f(); } catch { return fallback; } }

إمتى هتحتاج كل ده؟ LINQ في كل مكان (Where/Select/OrderBy)، الـ middleware، وIOptions configuration lambdas (services.Configure(o => o.X = 1))، والـ resilience libraries (Polly) كلها delegates.
